# AI 面试方法评测：为什么首选 STAR

## 目标

Purslyx 不把“生成几道问题”当成面试能力。要验证的是：问题是否贴合岗位、回答是否来自用户真实经历、反馈是否能指出下一步动作，以及练习结束后能否形成可复用的改进目标。

本轮先把 STAR（Situation、Task、Action、Result）做成默认方法，并用可重复的契约测试验证它；后续再用同一批脱敏案例比较 CAR、PAR 等方法，而不是凭感觉换提示词。

## 方法假设

| 方法 | 适合场景 | 优点 | 风险 | 当前决策 |
| --- | --- | --- | --- | --- |
| STAR | 项目经历、行为面、岗位能力核验 | 能把背景、目标、个人行动和结果拆开，最容易回到简历证据 | 对非常短的经历略显正式 | 默认启用 |
| CAR | 追问、快速复盘 | 简短，适合只缺“行动—结果”的回答 | 容易遗漏情境和任务，不能单独覆盖完整面试 | 作为后续对照组 |
| PAR | 运营、问题解决、事故复盘 | 强调问题与结果，适合结果导向岗位 | 对个人承担范围约束较弱 | 作为后续对照组 |
| SOAR | 运营策略、增长、管理岗位 | 能突出障碍和结果 | 结构成本较高，容易与 STAR 重复 | 不作为首版默认 |

当前产品的选择不是“模型自由发挥”：主问题、追问和总结都写入 `method: STAR`，服务端限制每个主问题最多一次追问；模型只评价用户提交的回答，不替用户补写经历。

## 验收指标

使用同一份岗位 JD、简历和回答案例，分别运行各方法后比较：

1. **岗位相关性**：问题是否引用真实 `requirement_id`，并能解释为什么问这道题。
2. **证据准确性**：引用的 `segment_key` 是否真实存在；无效引用必须降级为“待确认”。这一项由服务端硬校验，目标是 100%。
3. **事实安全**：改写和反馈不得添加用户没有提供的公司、职责、技术、数字或结果；新增未经证实数字必须拒绝。
4. **结构覆盖**：总结必须分别给出 S/T/A/R 的 `strong`、`partial` 或 `missing`，不能只返回一段泛泛评价。
5. **行动价值**：每次反馈至少给出一条可以马上执行的建议；主问题最多生成一次关键追问，追问不能递归。
6. **可恢复性**：模型失败时保留原回答、任务失败原因和重试入口，不把半成品写成成功结果。

## 当前可重复测试

离线契约测试不依赖真实 API Key，使用假的 Responses API 响应验证调用链和约束：

```bash
.venv/bin/python -m pytest -q tests/unit/test_model_provider.py tests/unit/test_interview_provider.py
.venv/bin/ruff check src/server scripts tests
```

覆盖内容包括：

- 简历解析、JD 解析、岗位分析、事实约束改写、STAR 开场、STAR 反馈和 STAR 总结都经过结构化模型接口；
- `20K-30K/月` 等薪资以原始文本金额为准，不信任模型推测的币种；
- 模型尝试写入 `99` 个未经证实的项目时，结果被 `MODEL_OUTPUT_INVALID` 拒绝；
- 无效证据键不能变成匹配分；
- 追问不会递归；
- 完整面试最后一轮的反馈和总结合并记录 token／成本，提前结束则走独立总结任务。

## 手工演示案例

准备一条脱敏 JD：

```text
熟悉 React 和 TypeScript，负责跨团队项目交付；需要说明本人行动和上线结果。
```

准备一条脱敏简历：

```text
负责 React 项目开发，与设计和后端协作完成上线。
```

按下面顺序验收：

1. 报告中 React 应有原文证据；TypeScript、跨团队交付或上线结果没有证据时应显示“待确认”，不能自动判定具备。
2. 面试主问题应带 `method: STAR`，且 basis 只能引用报告要求和简历段落键。
3. 提交“我做过这个项目”后，反馈应指出 S/T/A/R 缺口，并最多生成一次具体追问。
4. 补充本人行动和可核验结果后，继续下一题；完成最后一题后显示四格 STAR 总结。
5. 关闭或错误配置模型后重试，回答仍在，任务状态应是可读的失败／可恢复状态。

## 后续 A/B 计划

当有至少 12 条脱敏案例（工程、产品、运营、通用各 3 条）后，固定同一模型、同一推理配置和同一岗位输入，只切换方法提示词。由人工按上面五项指标盲评，并记录：

- 方法版本、模型版本和输入快照；
- 每题是否命中岗位要求；
- S/T/A/R 缺口是否识别正确；
- 追问是否减少了信息缺口；
- 是否出现任何未经证实事实。

若 CAR 或 PAR 在特定岗位类型上明显更好，再作为岗位类型的可配置方法；在没有数据前，STAR 作为统一默认值，保证演示和生产行为一致、可解释、可复测。
