# 明日 SDD 演示脚本

## 开场（30 秒）

“今天展示的是已经可以操作的完整前端工作台。需求先变成 Feature Spec，再变成接口和数据库事实，
最后用 201 环境的真实 HTTP 冒烟证明它能跑；现场从完整工作台里挑一个模块深讲。”

## 1. 先确认环境（30 秒）

浏览器打开 `http://127.0.0.1:8001/health`，现场指出：

```json
{
  "status": "ok",
  "database": {"backend": "postgresql"},
  "environment": "201"
}
```

补一句：“本项目禁止 SQLite；密码不在代码里，按 `本地开发环境.md` 注入进程。”

## 2. 先扫一遍完整工作台（45 秒）

登录后快速展示对应身份的菜单：

- 求职端：工作台、简历与期望、匹配池、岗位版简历、面试练习、用量、统计；
- 招聘端：工作台、候选人资料、用量、统计；
- 授权账号：站点概况、用户管理、角色权限、次数管理、日志管理。

说明：“这些入口都已接真实接口和状态；今天不逐页念菜单，而是选一个模块讲透。”

## 3. 选择一个模块深讲（2 分钟）

推荐讲“匹配池 → 完整报告”：打开岗位详情，展示浏览器草稿或手动 JD、岗位期望选择、分析状态、
固定维度、逐条证据、待核实事项、针对性面试问题、分析历史和去投递入口。

可替换为：

- “改写 → 岗位版简历”：事实补充、逐段采用／保留原文、模块排序、排版参数和 PDF 下载；
- “面试练习”：逐题回答、追问、刷新恢复、提前结束和完整总结；
- “管理员日志”：日期／账号／结果筛选、详情和导出任务轮询。

## 4. 页面走一条可复跑链路（2 分钟）

打开 `http://127.0.0.1:8001/`，点击“确认资料并生成匹配报告”。页面会完成：

1. 提交简历文字；
2. 提交岗位 JD；
3. 确认两份资料；
4. 对已确认版本生成报告。

展示输出中的 `resume_version`、`job_version`、`ability_score`、`evidence_coverage`、`conditions`，以及报告下方的“待核实事项与针对性面试问题”；强调问题来自报告依据，不是前端临时拼接。

## 5. 讲 SDD 追溯（2 分钟）

打开 [Feature Spec](../01-product/specs/Feature%20Spec-资料确认与可复核匹配.md) 和 [追溯矩阵](../02-technical/SDD追溯矩阵-最小演示.md)：

- 需求：用户要“知道哪些岗位值得投，并且有依据”；
- 接口：`POST /documents`、`POST /documents/{id}/versions`、`POST /job-pool/items`；
- 数据：草稿和确认版本分开，报告保存输入版本与规则版本；
- 实现：`api.py` 负责权限和事务，`matching.py` 计算分数；
- 验收：同键重试不多扣，跨账号返回 404，删除后旧入口失效。

## 6. 展示正式能力（2 分钟）

运行：

```bash
PURSLYX_BASE_URL=http://127.0.0.1:8001 \
PYTHONPATH=src .venv/bin/python scripts/smoke_201.py
```

只需要看最后一行 JSON：`environment=201`、`analysis_status=available`、`pdf_ready=true`、`browser_draft_deduped=true`、`apply_status=303`、`cross_account_isolation=true`。

## 7. 收尾边界（1 分钟）

“今天交付的是完整可操作的前端工作台和可复核的 SDD 主闭环，不把本地确定性模型说成真实模型效果，
也不把 303 说成平台已投递。下一步可以替换模型、Worker 和真实平台适配，但不需要推翻资料版本、任务、
用量和报告契约。”
