## 3. 对 Purslyx 的采用边界

### 浏览器侧岗位获取

Purslyx 自行实现只处理当前打开 JD 的篡改猴脚本。可以借鉴页面变化后的重新识别、可见元素过滤、失败即停、fixture 测试和手工检查方法。实现必须继续遵守以下边界：

- 自动同步的是 Purslyx 受限会话，不保存招聘平台密码、Cookie 或令牌。
- 自动获取直接写入匹配池，不绑定简历／期望，也不消耗分析次数；用户点击匹配时再选择输入。
- 不批量遍历岗位，不自动沟通、代填、投递、回复或绕过验证码与风控。
- BOSS 与猎聘分别维护适配层、样例 DOM 和失败状态；页面结构变化时保守提示用户粘贴。

### 简历编辑与 PDF

`cool-resume` 的版本结构、模块渲染、分页和导出流程可作为实现参考。Purslyx 仍按已评审架构使用 Vue 3、Tiptap、服务端版本记录和 Chromium 成品导出：

- PostgreSQL 保存账号归属、岗位版版本和排版参数，浏览器存储不作为业务事实来源。
- 即时编辑预览与正式 PDF 使用同一内容、模板和排版版本。
- 渲染层只接受允许字段和样式，转义用户文本，禁止用户脚本和任意外部资源。
- 若采用参考项目源码，先处理依赖安全告警、许可证声明和与 Vue／服务端版本模型的差异，不整体复制其构建配置。

### 匹配池、状态和统计

`jobflow-for-codex` 的规范化状态、稳定 ID、原子 upsert、未知别名告警与不覆盖源数据的迁移思路，适合转换成 Purslyx 的数据库约束、服务事务和迁移测试。其“已沟通、已发简历、招聘者回复”等状态属于后续投递台账能力；首版统计仍只记录 Purslyx 服务端成功写入的“去投递点击”，不推断平台投递结果。

## 4. 比赛交付与商业首版的关系

[参赛规则](../00-overview/event/黑客松规则与赛题说明.md)要求赛题二跑通一个轻量完整流程，并选择一处重点打磨。为控制七天交付风险，比赛验收顺序如下；该顺序不删除[需求说明](../01-product/specs/需求说明.md)中的商业首版范围。

| 层级 | 本项目内容 | 验收处理 |
| --- | --- | --- |
| 官方最低流程 | 一份 JD、一份脱敏简历、岗位要求与经历依据、至少一段事实改写、3 道面试题、至少一轮回答反馈 | 必须先形成可重复运行的纵向流程，并覆盖信息缺失、换岗位和拒绝编造场景 |
| 比赛增强体验 | 当前 JD 自动获取、私有匹配池、多条岗位期望、完整分析报告、岗位版简历和 PDF | 在最低流程稳定后接入；演示时只展示已经真实运行的部分 |
| 商业化基础 | 固定身份账号、使用次数、异步任务、删除清理、管理端权限、统计与日志 | 继续按产品基线设计；未在截止前实现的部分如实标记为后续，不用于证明比赛完赛 |
