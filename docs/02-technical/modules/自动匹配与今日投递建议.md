# 自动匹配与今日投递建议

更新：2026-10-11。规则为 `auto-matching-v1`、`application-recommendation-v1`。

首页现已改为[跨日待投机会与处理状态](跨日待投机会与处理状态.md)，默认近 30 天未处理；本文件的今日建议接口保留兼容，自动匹配与今日进度口径不变。

## 使用边界

求职账号在工作台弹窗选择自己的已确认简历、1–10 套有效岗位期望和每日上限（1–50，默认 10），明确勾选自动扣次授权。默认关闭；开启不回扫历史岗位。开启后的浏览器新抓取立即入池、冻结输入并按额度排队。手动匹配和招聘流程保持原样。

每个岗位成功交付匹配报告计 1 次分析额度；入队预留，失败或来源删除释放。JD 解析和匹配是两次模型调用，用户仍只计一次，后台成本累计两次。额度指可用分析次数，不是账户货币余额。不自动抓取用户未打开的页面，不自动投递，不联系招聘者。

## 数据与事务

- `auto_matching_configs`：账号唯一的授权设置、默认简历、期望公开 ID、每日上限、确认时间和修订号。设置 PUT 必须校验修订号、CSRF、账号归属和幂等键。
- `auto_match_jobs`：岗位唯一，以及账号＋平台／规范化 URL 摘要唯一；保存冻结的简历版本、期望版本、原请求 ID、排队日期和 Analysis／Task 引用，不复制正文。
- 状态仅为 `waiting / enqueued / cancelled`。实际执行、成功、失败沿用原 `analysis` 任务，不另造执行状态机。
- 同一账号的抓取、领取、设置和删除在账号行锁下串行判定；分析、功能次数预留、自动领取和 outbox 同事务提交。重复上传、重复内容及同来源更新均不再自动领取。需要重新分析更新后的 JD 时，用户手动确认。
- 新抓取使用所选资料的最新已确认版本；已经等待／排队的岗位不自动切换输入。多套期望按整体最适合的一套对照，不跨方案拼接条件。
- 每日上限按上海自然日计算首次自动领取数量，包含失败领取和随后删除的领取，防止失败／删除绕过上限。人工重试沿用同一任务，不额外领取；成功任务不可重试。
- 余额不足、任务队列满、每日上限、站点预算或模型价格缺失保留 waiting。Worker tick 恢复条件后继续；模型执行失败不会自动反复调用，用户到任务中心重试。
- 暂停保留 waiting 并停止新领取；已经领取的任务继续交付。删除岗位、简历、分析或所用期望会取消待执行任务并注销自动领取，迟到结果与重试不得复活。

## 执行与费用

独立 Worker 每轮先调度 waiting，再消费原 outbox。账号扫描每轮最多 100 个并按 ID 轮转，避免长期无额度账号阻塞后续账号。默认 inline 模式在响应之后执行账号限定的自动任务，同时由服务启动的轻量循环处理跨日、补次、队列恢复和重启后的 outbox，循环复用 Worker 保留扫描游标。后台循环只消费已授权的自动任务，不消费无关手动任务。账号并发受现有运行上限控制；预算仍由原全站预算预留保护。

自动流程：从保存的 JD 原文结构化抽取 → 用冻结简历／期望匹配 → 原文证据校验与确定性计分 → 保存派生 `parsed_job` 和投递建议。不覆盖原始 JD 版本。

OpenAI-compatible Chat Completions 使用明确的 `max_completion_tokens`：抽取最多 4,000，匹配最多 8,000。预留覆盖两次调用的 UTF-8 输入上界、第二次 80,000 字符 JSON 限制和指令余量。成功累计两次 token；第二次失败保留第一次消耗，未知供应商用量保留未知预算，不当作零成本。配置模型不变，不调用额外模型生成投递分类。

## 接口

| 接口 | 契约 |
| --- | --- |
| `GET /api/v1/job-pool/automation` | 当前账号设置、有效性、今日自动领取数量、可用分析次数、时区与修订号 |
| `PUT /api/v1/job-pool/automation` | `enabled / resume_document_id / preference_ids / daily_limit / base_revision / confirm_usage`；开启必须明确确认扣次，账号会话＋CSRF＋幂等键 |
| `GET /api/v1/job-pool/recommendations?limit=50` | 今日新增或今日完成分析的岗位，四类建议、原文依据、风险、核实项、报告和主动去投递入口；限制 1–100，超限明确标识截断 |
| `POST /api/v1/browser/job-drafts` | 受限浏览器会话；响应增加 `automatic_processing` 中文状态，无简历正文、报告正文或去投递签名令牌 |
| 原任务与去投递接口 | 复用原轮询、失败重试和有签名的主动点击；浏览器会话不能读取自动设置／建议或用户用量 |

`progress.captured` 为今日实际入池的浏览器岗位；`completed` 为当前日范围内可读的最近完成报告数；`active / waiting / failed` 包含之前保留的自动任务。只展示最近报告有效的岗位，不把处理中或失败伪装为匹配不足。

## 投递规则

优先级依次判定：

| 条件 | 结果 |
| --- | --- |
| 有必须满足的条件冲突 | 暂缓投 |
| 必须满足的条件未知 | 先核实 |
| 分数或覆盖率不可解释，或覆盖率低于 60% | 先核实 |
| 匹配依据分至少 75，覆盖率至少 70% | 优先投 |
| 匹配依据分至少 55 | 可以尝试 |
| 其余有足够依据但匹配较弱 | 暂缓投 |

可协商的未知条件列为风险，不机械阻止所有岗位投递。依据只引用原报告的有效简历段落，未知不等于能力差距。阈值是个人精力排序启发式，不是招聘方评分或录用概率。用户点击去投递才记录点击并打开原页面，不计为实际提交成功。
