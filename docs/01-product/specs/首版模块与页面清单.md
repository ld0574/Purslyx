这份清单只回答三个问题：有哪些模块、两类用户怎样完成任务、工作台菜单打开哪些页面。注册时须选择“求职”或“招聘”；首版身份固定，没有工作区切换，另一身份需要用另一邮箱注册。求职者有自己的私有匹配池；招聘者只分析一个岗位与一位候选人，不建立候选人池。

首版必须完成 BOSS 直聘与猎聘当前岗位获取、逐条匹配打分、完整文字面试，以及从匹配池跳转到原岗位详情的“去投递”入口与点击统计。管理端的用户、后台权限、次数发放和站点概况也属于首版。用户进入原平台后自行决定是否投递；Purslyx 不代填、不自动提交，也不监控平台投递进度或回复。公开岗位市场、后台爬取岗位、跨岗位推荐、真实支付和企业团队功能不在首版范围。[首版高保真产品稿](../prototypes/高保真产品稿.html)和[篡改猴高保真产品稿](../prototypes/篡改猴高保真产品稿.html)按本清单生成；菜单和页面范围仍以本清单为准。

## 一、模块与功能

模块名固定为下表的短名，后续文档也按这些名字命名。“简历”负责资料、多条岗位期望、事实补充、改写和 PDF；“匹配池”负责求职者保存的岗位、匹配进度和每条岗位的独立分析报告，浏览器脚本是匹配池的输入入口。管理端使用“用户”“用量”“统计”“日志”：分别管理账号与后台权限、发放使用次数、查看全站概况、查询后台操作和运行记录。

| 模块 | 负责什么 | 首版功能列表 |
| --- | --- | --- |
| 用户 | 管理固定身份的账号和私有数据 | 邮箱密码注册时选择求职或招聘、邮箱验证与找回密码、登录退出；首版不切换身份；重新登录后恢复本账号资料与历史；按账号隔离访问；删除前预览影响。授权管理员可搜索和查看用户，管理独立的后台角色与权限并留操作记录；注册身份固定，不能通过后台改成另一身份。 |
| 简历 | 管理简历资料、岗位期望、真实改写和岗位版成品 | 求职者导入并确认自己的简历；可保存多条相互独立的岗位期望，每条同时包含岗位方向、地点、办公方式、薪资和条件强度，分析前选择其中一条生成快照。根据匹配池报告补充真实事实，确认消耗后生成逐段建议；查看原文、建议、理由和事实依据，手动编辑、采用或保留原文，再调整模块顺序、字体、字号、间距与加粗，预览并导出同版本 PDF。招聘者在这里导入单个 JD 与候选人简历，并查看单人报告和待核实问题。 |
| 匹配池 | 收集求职者岗位，并逐条展示匹配结果与报告 | 篡改猴自动同步 Purslyx 登录状态；求职者打开 BOSS 直聘或猎聘受支持的 JD 详情页后，脚本自动识别并直接写入匹配池，也可手动粘贴。抓取入库不绑定简历／期望、不计次；用户点击“匹配”时再选择本次使用的简历与岗位期望并确认一次分析消耗。岗位详情统一提供匹配概览、完整报告、原文与输入版本、制作岗位版简历和“去投递”；求职端不在“简历”菜单重复放分析报告。 |
| 面试 | 围绕一个已确认岗位完成文字练习 | 生成三道主问题，每题最多一次承接回答的追问；逐轮反馈、提前结束、完成汇总和中断续答；未回答部分明确标记，不重复扣除使用次数。 |
| 任务 | 让耗时操作可查看、重试和恢复 | 导入、分析、改写、导出与面试显示排队、执行、待补充、失败和完成；重复点击回到原任务，断线或重新登录后可继续；失败保留输入。 |
| 用量 | 管理各功能的剩余次数和发放记录 | 求职账号默认有分析 20 次、改写 20 次、面试 5 场，招聘账号默认有分析 20 次；执行前展示消耗与剩余次数，成功只扣一次，失败释放预留；免费操作不扣次数；频率、并发和每日预算受限时提示并保留输入。授权管理员可按适用功能给指定用户追加次数，填写原因并查看发放与使用记录。 |
| 统计 | 查看使用、去投递跳转与产品反馈 | 求职者查看本人今日“去投递”点击数，招聘者查看自己的候选人分析次数；两类用户可提交对 Purslyx 的使用反馈。授权人员查看全站概况、注册用户、按日期／身份／功能汇总的使用、成本、去投递点击和产品反馈；点击数不当作平台实际投递成功数。 |
| 日志 | 供授权人员查询后台操作、安全事件和任务运行记录 | 管理端按权限查看管理操作、登录安全和任务运行日志，按日期、账号、对象、结果和关联 ID 筛选并查看详情；角色权限与次数变更保留前后值，任务日志保留状态、耗时和重试，不在日志中保存简历、JD、回答、密码或令牌正文；导出本身也留操作记录。 |

统计口径写作“去投递点击数”：服务端校验并记录一次用户点击，随后返回原岗位详情的跳转；无法确认浏览器是否收到跳转响应或外部网页最终加载。刷新、同一点击的重复请求、保存岗位或导出 PDF 不新增计数。这个数字表示 Purslyx 带来的投递意向，**不能写作“已投递简历数”或平台成功投递数**。平台的实际提交、回复和面试进度由用户在原平台查看，首版不自动读取。产品反馈指用户主动评价 Purslyx，与去投递点击数分别统计。

## 二、主流程怎么跑

注册、验证和登录后，用户直接进入注册身份对应的工作台。工作台显示近期内容和未完成任务，具体操作在菜单页面完成；不会出现切换到另一身份的按钮。获授权人员另有管理端入口，注册身份仍固定。所有计次 AI 操作都先展示消耗和剩余次数，任务进行中可离开页面，之后从工作台或历史恢复。

**求职流程**

1. 从“简历”导入并确认自己的简历，按岗位方向保存一条或多条求职期望。例如“前端工程师＋杭州／远程＋20–30K”和“后端工程师＋杭州现场＋30–40K”是两条独立条件组合；分析前选择本次使用的一条。未填写保持“未知”，不能当成“不限”，不同期望的字段不能拼接使用。
2. 登录 Purslyx 后，篡改猴自动同步登录状态。打开 BOSS 直聘或猎聘受支持的 JD 详情页，等待脚本自动识别、获取并提示“岗位信息获取完成”；岗位直接写入自己的匹配池。页面不支持或自动获取失败时可在“匹配池”手动粘贴。
3. 在匹配池点击某条岗位的“匹配”，再选择一条岗位期望和本次使用的简历，并确认这次分析会消耗一次分析次数。简历、期望和剩余次数都满足时排队打分；缺资料、可用次数或全站预算时保留为“待分析”，补齐后再确认消耗并分析。每条岗位分别有报告，不自动比较或推荐多个岗位。
4. 打开匹配池里的岗位，从“完整报告”阅读能力维度、固定权重、原文依据、所选岗位期望、条件对照和整体建议，并从“原文与版本”核对输入。需要优化表达时由报告进入“简历”的改写流程，补充真实事实、确认消耗 1 次改写机会、逐段比较原文与建议及理由，编辑、采用或保留原文，再调整岗位版模块与排版并下载 PDF；也可从“面试”开始或恢复文字练习。
5. 从匹配池岗位详情点击“去投递”，Purslyx 记录一次点击并发起跳转到该岗位在 BOSS 直聘或猎聘的原详情页。用户在平台页面自行投递和查看回复；返回 Purslyx 不需要等待脚本识别投递状态。
6. 从“统计”查看今日去投递点击数并提交产品使用反馈，从“用量”查看剩余次数；资料、岗位和历史可重新打开，删除前先确认关联影响。

**招聘流程**

1. 注册时选择招聘身份，从“候选人简历”导入一份岗位描述和一位候选人的简历，检查并确认提取内容与岗位条件。
2. 候选人明确提供期望时才填写岗位方向、地点／方式与薪资，并记录来源；未提供的项目标为“未知”，不替候选人推断。
3. 确认消耗一次分析次数，查看能力分及原文依据、条件冲突、待核实事项和面试问题。报告供招聘者人工判断，不自动淘汰或录用，也不进入求职者的匹配池、改写和面试练习。
4. 从“候选人简历”重新打开原报告及所用资料版本；条件变化时明确确认后另开一次分析。从“统计”查看自己的分析次数，从“用量”查看剩余次数。

实现上先打通用户、任务和用量，再完成简历与招聘单人分析，随后完成匹配池、两站浏览器输入和去投递跳转、面试，最后联验管理端和统计。顺序只表示依赖，上述首版功能都要完成。桌面端覆盖全流程；手机至少能登录、上传或粘贴资料、确认条件、发起并阅读分析、回答面试、阅读和下载 PDF，以及查看匹配池与原岗位链接。复杂简历排版和浏览器脚本以桌面为主。

## 三、模块页面与工作台菜单

**求职工作台菜单**：工作台 → 简历 → 匹配池 → 面试 → 用量 → 统计。

**招聘工作台菜单**：工作台 → 候选人简历 → 用量 → 统计。

**管理端菜单**：站点概况 → 用户管理 → 角色权限 → 次数管理 → 日志管理。入口仅向有相应后台权限的账号显示；每页再次校验操作权限。这五个菜单分别属于统计、用户、用户、用量、日志模块。

“候选人简历”和“简历”由同一简历模块按账号身份展示不同功能。右上角账号菜单提供本账号信息、退出及授权人员可见的“进入管理端”，没有身份切换。“任务”显示在发起页，工作台有继续入口，不占单独菜单；浏览器侧界面在 BOSS 直聘和猎聘受支持的 JD 详情页自动出现并运行，不设置“获取岗位”按钮作为正常入口。

下表按模块列出页面与界面，菜单名就是原型需要呈现的入口。各私有页面都要校验账号归属；已删除内容从旧入口打开时显示不可访问。空内容、处理中、失败和完成状态都需用文字说明，失败时保留可恢复的输入。
